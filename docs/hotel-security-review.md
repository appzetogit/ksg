# Hotel vertical: security and correctness review (phase 9, workstream D)

Scope: `Backend/src/modules/hotel/**`, the hotel touch points in `Backend/src/core/**`
(Razorpay webhook, payments facade, auth middleware, private files, ledger) and
`Frontend/src/modules/Hotel/**`, as of `0b594f2` (hotel phases 1-5 merged).

Method: adversarial read of every route, controller, service and validator, then a
failing regression test per confirmed finding in `Backend/tests/hotel.security.smoke.mjs`
(`npm run test:hotel-security`, also in the `test` chain).

## Findings

| 1 | High | Money / refunds | `applyRefund` capped refunds against a booking read *before* the refund, and wrote the new `walletRefunded` / `gatewayRefunded` / `refundedAmount` as absolute `$set` values. ### Verified, no change needed

- **AuthZ / IDOR**: every customer route loads bookings with `{ _id, userId }`; reviews check `booking.userId`; saved properties are keyed on the user. Every partner route scopes by `partnerId` (bookings) or `loadOwnProperty` / `loadOwnRoomType` (properties, room types, inventory, blocks, review replies); money routes use `req.user.userId`. Pending/blocked partners are refused (`requireApprovedHotelPartner`, auth middleware). Admin routes sit behind `ADMIN` + `requireServiceAccess('hotel')`. Covered by [3].
- **Razorpay verify** checks the HMAC signature, then fetches the payment and checks `order_id`, `status === 'captured'` and the captured amount (paise) against the booking's online amount. The core webhook verifies its signature with a constant-time compare over the raw body. Verify and webhook are idempotent on the payment id; the transition is atomic on `status` + order id. Covered by [7] and `hotel.booking.smoke`.
- **Cancel vs verify race / expiry vs late payment**: whichever transition wins, the loser's money goes back (`refundLateCapture`), and inventory is released in the same transaction as the status change. Covered by [7] and [8].
- **Wallet** debits/credits are idempotent on `referenceKey` and guarded by an atomic balance check. Covered by [7] (double cancel credits once).
- **Withdrawals**: the hold is an atomic ledger `$inc`; a request that drives the balance negative is released and refused. Covered by [7] (4 parallel requests, one succeeds).
- **Inventory**: reserve is a per-night conditional `$inc` inside a transaction with compensation for standalone servers; every exit path (cancel, expire, no-show, check-out, partner/admin cancel, create failure, gateway order failure) releases through `transition()`. Capacity reductions below booked units are refused. Covered by [8].
- **State machine**: one transitions table, atomic `findOneAndUpdate({ _id, status: from })`, history entry with actor on every change; admin overrides (`force`) are noted in the history.
- **Input validation**: zod on every write endpoint, unknown fields stripped (client prices ignored), ObjectId checks before queries, regex input escaped, `mongo-sanitize` strips `$` keys and the zod enums/ids then reject the object (400), page size capped at 100, 30-night cap, past dates refused. Covered by [4].
- **Data exposure**: customer pricing drops commission/payout (`customerPricing`), voucher never prints them, public reviews show the first name only, admin partner JSON drops FCM tokens; bank numbers are stored masked only.
- **Bed capacity (hostels/PG)**: search's undated pre-filter uses `totalInventory × bedsPerRoom` for bed room types, which is exactly `HotelRoomType.sellableUnits()`, the capacity written to inventory-day rows (and re-applied from today on by `applyCapacity` when the room type changes). With dates, search, `/availability`, quote and `reserve()` all read the same inventory-day rows (`capacity - booked`, `closed`), and a missing row means full sellable capacity in all of them, so they cannot disagree. The only gap is by design: an undated search can list a property whose upcoming nights are all closed; the dated search and the booking itself refuse it.
- **Frontend**: no `dangerouslySetInnerHTML`, no token logging in `Frontend/src/modules/Hotel/**`.

## Deferred (with recommended fixes)

| # | Severity | Finding | Why deferred | Recommended fix |
|---|----------|---------|--------------|-----------------|
| D1 | Medium | KYC / property document fields (`kyc.*Front/Back/panImage/gstCertificate`, `documents[].fileUrl`) legitimately hold private paths, but nothing proves the file was uploaded by this partner: a partner who knows another account's private path can store it and receive a signed link. | Needs upload ownership in core (`core/upload`), shared by every vertical. | Record `{ path, ownerRole, ownerId }` when a private file is uploaded; accept a private path in these fields only if the caller owns it (or an admin); make `privateFileLinks` sign only paths the caller may read. |
| D2 | Medium | Pay-at-hotel bookings hold inventory with no money at all, so the 3-hold cap does not stop one account from booking many rooms "pay at hotel" and never showing up. | Lives in the quote/create path that the coupons workstream is changing. | In `createBooking`, before reserving: refuse when the user already has N (e.g. 3) upcoming unpaid `pay_at_hotel` bookings, or more than M rooms per property-night; optionally require `partial_prepaid` above 2 rooms. Return 409 `too_many_unpaid`. |
| D3 | Medium | A partner can change the bank account and request a withdrawal straight away; a stolen partner session can redirect payouts. | Product/ops decision (re-verification flow). | On `PUT /partner/me` with a changed `bank`, set `bank.verifiedAt = null`, notify the partner by SMS, and refuse withdrawals until an admin re-verifies (or for 72 h). |
| D4 | Medium | A refund that fails at the gateway or wallet is recorded as `refunds[].status = 'failed'` with no automatic retry; an admin must notice it. | Needs a retry design (re-claim of the unpaid part under the same key). | Admin "retry refund" action + a job that retries `failed` entries with backoff, re-using the key and moving only `amount - (walletAmount + gatewayAmount)`. |
| D5 | Medium | Settlement runs on in-process booking events; if a ledger append fails (DB blip) the booking is never settled and nothing retries. | Cross-cutting with the ledger nightly job. | Nightly reconcile: for bookings in `settleOn` or later (and cancelled/no-show) without the matching `hotel_booking:<id>:settle|retained` rows, re-run `settleBooking` / `settleCancellation` (both idempotent). |
| D6 | Low | `settleCancellation` runs on the `transition` event, before the cancellation refund is paid, and treats `cancellation.refundAmount` (the preview) as refunded. If the refund is clamped or fails, the retained share is under-settled. | Settlement workstream; small effect. | Settle cancellations from the `refund` event (or after `applyRefund` returns) using the refunds actually processed. |
| D7 | Low | The expiry job expires a hold without asking Razorpay whether a capture is in flight; a slow webhook turns a good payment into "expired + refunded". | Needs a gateway call per expiring hold. | Before expiring, fetch the order's payments; if one is captured, confirm instead of expiring. |
| D8 | Low | The hold cap is count-then-insert, so a burst of parallel creates can exceed it by a few. | Rate limiter and per-request latency make this marginal. | Per-user counter document incremented in the create transaction. |
| D9 | Low | Partners may check a guest out with `force: true` and an unpaid balance (recorded in history only). | Product decision. | Require a reason and surface it in admin reporting. |
| D10 | Low | `property.contactNumber` is shown publicly; partners may enter a personal number. | Intended as the hotel's public phone. | UI hint in the partner wizard, or show it only on a confirmed booking. |
| D11 | Info | Legacy `?token=` voucher path still accepted. | Old app builds in the field. | Remove after the `vt` link has been live for one release. |
| D13 | Low | Core `/api/v1/fcm-tokens/*` (register/remove a device token) refuses role `HOTEL_PARTNER`; partners can register a token only at verify-otp and remove it only via logout. | Core endpoint shared by all roles. | Teach the core FCM-token routes the `HOTEL_PARTNER` role (bucketed `fcmTokens.web/app`, max 5 per bucket as at verify-otp). |
| D12 | Info | Global `xss-clean` HTML-escapes stored strings (a guest "O'Brien" is stored as `O&#39;Brien` and the voucher shows the entity). | Platform-wide middleware. | Escape on output (React, voucher `esc`) and drop `xss-clean` for JSON APIs. |
